# Devil Summoner: Raidou Kuzunoha 1 and 2

A work-in-progress matching decompilation of *Shin Megami Tensei: Devil
Summoner* (Raidou Kuzunoha vs. the Soulless Army) and *Shin Megami Tensei:
Devil Summoner 2* (Raidou Kuzunoha vs. King Abaddon) for PlayStation 2. Both
games run on the SMT3 engine, so this repository is set up from
[smt3-decomp](https://github.com/Megami-Decomps/smt3-decomp) and carries two
versions in one tree the way
[dds-decomp](https://github.com/Megami-Decomps/dds-decomp) does.

Building requires your own copy of the games. Disc images and retail
executables are not included, and nothing derived from them is committed.

## Status

Both versions rebuild byte-identical to the retail executables. Most code is
still assembly split from them (`INCLUDE_ASM`); the functions that are C were
carried from SMT3 and DDS wherever the Raidou code is the same.

Functions and code bytes from C, from `python3 tools/progress.py --markdown`.
"Game" units are Atlus code, "sdk" units are the Sony libraries and C runtime.
The game rows split by what the unit was found in (`config/<version>/tu_evidence.tsv`):
a unit that is in SMT3, one that is in DDS and not SMT3, or neither. VU
microcode and hand-written assembly are not counted.

## Shared with SMT3 and DDS

Both Raidou games run on the SMT3 engine, and about 1,500 more functions per
game are the same code as DDS1 and DDS2. Where the code is identical, the
decompiled C comes from those repositories:

- **Names.** A Raidou function takes the name of its SMT3 or DDS counterpart.
  `config/<version>/name_sources.txt` records each name's source and evidence.
  SMT3's name wins where both have one. See [docs/smt3-names.md](docs/smt3-names.md).
- **Translation units.** `.text` is split into one unit per TU, tied to the
  SMT3 or DDS unit it was found in, with asm gaps where there is no evidence.
  See [docs/tus.md](docs/tus.md).
- **One file per TU.** A TU has its C inline, in link order, with
  `INCLUDE_ASM` for functions not yet written. A TU whose text is the same in
  both games is one file, `src/shared/<unit>.c`, compiled into each version.
  A TU that differs is `src/<version>/<unit>.c`, and that file wins.
- **Ported C.** `tools/raidou_c.py` and `tools/raidou_dds.py` copy a body
  verbatim from smt3-decomp (else dds-decomp) when the Raidou function is word
  for word the same, along with the declarations the TU needs, and check the
  result against retail. Functions that do not compile to the same bytes stay
  assembly (`config/<version>/smt3_c.tsv` says why). SMT3 is authoritative:
  where DDS declares a name SMT3 also declares, SMT3's declaration is used.
  See [docs/shared-c.md](docs/shared-c.md).

These two repositories are read-only inputs to the port tools; the ported C
lives here.

## Toolchain

The build uses smt3-decomp's compilers: ee-gcc 2.96 (`2.96-ee-001003-1`) for
game code and ee-gcc 2.9 (`991111-01`) for the Sony libraries. Evidence that
this is right for both games, so far:

- Both link the same Sony EE libraries as SMT3, all tagged `PsII... 2500`
  (SDK 2.5.0): libgraph, libdma, libpad, libcdvd, libmrpc, libipu, libmc,
  libkernl, plus libsdr.
- About 2,300 functions in each game are word-identical to SMT3's (strict
  matches in smt3-port's cross-game map), so their compiler and flags are
  SMT3's.
- `raidou2` contains C++ with exceptions (a 0x904-byte `.eh_frame` and a
  `.gcc_except_table`); its CIE has an empty augmentation string, which is
  GCC 2.x output (GCC 3 writes `zR`). `raidou1`'s `.eh_frame` is only the
  4-byte terminator, as in SMT3.

The build compiles the C and checks the linked result against the retail SHA-1.

## Building

Requirements: Linux x86-64 or WSL2 with 32-bit i386 support, Python 3.10+,
`ninja`, `cpp` and `git`.

```sh
python -m venv .venv && . .venv/bin/activate
python -m pip install -r requirements.txt
python tools/download_tools.py

# Copy the disc images into the repository root or orig/, then:
python tools/extract.py        # or copy each ELF to orig/<version>/<serial>
python configure.py            # every version with an ELF in orig/, or name one
ninja                          # or: ninja raidou1
python tools/progress.py       # source coverage
```

`ninja` ends by checking each linked ELF against `config/<version>/checksum.sha1`.
`tools/check_unit.py <unit.c>` compares one unit's objects with retail.
CI (`.github/workflows/check.yml`) cannot have the executables: it compiles the
scripts and runs `tools/check_config.py` on the tables and source layout.
