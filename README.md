A work-in-progress matching decompilation of *Shin Megami Tensei: Devil
Summoner* (Raidou Kuzunoha vs. the Soulless Army) and *Shin Megami Tensei:
Devil Summoner 2* (Raidou Kuzunoha vs. King Abaddon) for PlayStation 2. Both
versions are built from one tree. The build setup comes from
[smt3-decomp](https://github.com/Megami-Decomps/smt3-decomp).

Each translation unit is one file: `src/shared/<unit>.c` where the unit is
identical in both games and is compiled into each version, else
`src/<version>/<unit>.c`.

Building requires your own copy of the games. Disc images and retail
executables are not included, and nothing derived from them is committed.

## Status

Both versions rebuild byte-identical to the retail executables. Most code is
still assembly split from them (`INCLUDE_ASM`).

Functions and code bytes from C, from `python3 tools/progress.py --markdown`.
"Game" units are Atlus code, "sdk" units are the Sony libraries and C runtime.
VU microcode and hand-written assembly are not counted.

objdiff over every unit (`objdiff.json` is generated by `configure.py`, with
the categories `game` and `sdk` for each version); it needs the retail executables.

Both ELFs have entry `0x00100008` and keep their section headers. `gp` is
`0x00471770` in `raidou1` and `0x004E4170` in `raidou2`. The VU0 and VU1
microcode is assembled from the listings in `src/<version>/sdf/vu/`.

## Toolchain

The build uses ee-gcc 2.96 (`2.96-ee-001003-1`) for
game code and ee-gcc 2.9 (`991111-01`) for the Sony libraries. Evidence that
this is right for both games, so far:

- Both link Sony EE libraries, all tagged `PsII... 2500`
  (SDK 2.5.0): libgraph, libdma, libpad, libcdvd, libmrpc, libipu, libmc,
  libkernl, plus libsdr.
- `raidou2` contains C++ with exceptions (a 0x904-byte `.eh_frame` and a
  `.gcc_except_table`); its CIE has an empty augmentation string, which is
  GCC 2.x output (GCC 3 writes `zR`). `raidou1`'s `.eh_frame` is only the
  4-byte terminator.

The build compiles the C and checks the linked result against the retail SHA-1.

## Building

Requirements: Linux x86-64 or WSL2 with 32-bit i386 support, Python 3.10+,
`ninja`, `cpp` and `git`.

```sh
python -m venv .venv && . .venv/bin/activate
python -m pip install -r requirements.txt
python tools/download_tools.py

# Copy the disc images into the repository root or orig/, then:
python tools/extract.py        # or copy each ELF to orig/<version>/<serial>
python configure.py            # every version with an ELF in orig/, or name one
ninja                          # or: ninja raidou1
python tools/progress.py       # source coverage
```

`ninja` ends by checking each linked ELF against `config/<version>/checksum.sha1`.
`tools/check_unit.py <unit.c>` compares one unit's objects with retail.
CI checks the scripts and source layout without retail executables. When the
private inputs are available, it also verifies both builds and publishes the
[progress site](https://megami-decomps.github.io/raidou-decomp/) on pushes to
`main`. Badges count matched game and engine code bytes and functions, excluding
SDK code and assembly. `tools/progress.py` also includes SDK in its totals.

## Progress publishing

Set `ORIG_REPO` to `Megami-Decomps/raidou-orig` and `ORIG_DEPLOY_KEY` to a
read-only deploy key for that private repository. It must contain
`orig/raidou1/SLUS_214.31` and `orig/raidou2/SLUS_218.45`. Set the repository
Pages source to GitHub Actions. Without these secrets, CI runs only the checks
that do not need retail inputs.
